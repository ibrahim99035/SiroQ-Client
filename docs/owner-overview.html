The problem it solves

Pharmacies export dispensing and inventory records and email them as attachments; associations chase submissions across member sites; nobody can prove what was sent or whether it arrived intact. SiroQ replaces the email hand-off with a filed record that has a stable reference, a per-file SHA-256 checksum, a validated status, and a full chain of custody.

How the two services split

Application (Next.js) owns identity, tenancy, filings, uploads, audit history, reports, and the UI. Analytics Service (FastAPI) owns file parsing, profiling, classification, data-quality scoring, domain analytics, and forecasting. The client calls the analytics API only for analysis and series/forecast output; everything user-facing state lives in the application database.

Trust properties (built in, not bolted on)

  • Tenant scope is derived from the session on every request — no route trusts a client-supplied scope.
  • Status changes and their audit event are written in the same transaction.
  • Reports are immutable; correcting one requires reopening the filing, which is itself audited.
  • Files are validated against their actual bytes (ZIP container, RFC-4180 CSV parse), not their filename.
  • Raw documents are served only through an authorised endpoint, never a public URL.

Analytics philosophy

Every number is computed by a deterministic, registry-driven engine: content is classified from headers and value types, domain engines run per business category, insight rules aggregate, and a holdout-validated statistical forecast projects forward. There is no LLM, no external model call, and no raw data leaving the deployment. Forecasts are reproducible — the same file yields the same result.

Read this first: the two services are not yet connected in code

The analytics service is fully built, fully tested and independently deployable, and the application is fully built, fully tested and complete on its own — but no code in the application calls the analytics service yet. The repository's own .env.example states it explicitly: the ANALYSIS_SERVICE_* variables exist, default to ANALYSIS_SERVICE_ENABLED="false", and are annotated "NOT YET WIRED — no code in this repository reads these; setting them changes nothing today. The client, the API contract and the UI action still have to be written."

So the arrow between the two boxes above is planned, not live. This is the largest single gap in the product and the highest-value next piece of work — tracked as Phase 7 of docs/PLAN.md. Everything in sections 11–16 below is real, shipping, verifiable code; it is simply not yet surfaced inside the filing workflow.

Application — Next.js 16 (the product surface)

  • Next.js 16 App Router, React 18, Tailwind + the brand token set.
  • Custom server-side sessions: opaque random token in the cookie, only its SHA-256 digest stored, so reading the sessions table yields no usable credential. Cookie is httpOnly + Secure + SameSite=Lax, 30-day TTL, immediately revocable.
  • Prisma 7 over Postgres via the @prisma/adapter-pg driver adapter. (The service image ships the geoalchemy2 dependency, but no geometric column is in use in either schema today.)
  • Tenant scoping derived from the session on every API route (association / pharmacy) — never from the request body.
  • S3-compatible object storage via the AWS SDK, two drivers: neon (Neon Object Storage, branch-scoped so a preview branch cannot touch production) or local (filesystem, streamed back through a route).
  • Best-effort email (nodemailer) for invitations, status changes, report delivery.
  • Invites, redirects and notifications are wired; the simulated backend, latency/fault switch and in-memory store were deliberately deleted rather than narrowed.
deps: zod · bcryptjs · nodemailer · @aws-sdk/client-s3 · zustand · radix-ui

Analytics Service — FastAPI (the computation)

  • Standalone FastAPI app, published as a wheel/sdist and a GHCR image.
  • Key-authenticated via X-API-Key (constant-time compare, deny-by-default).
  • pandas-based ingestion and analysis; no database dependency of its own.
  • Reads uploaded bytes, returns analysis JSON, a client report, and on-demand series/forecast.
  • Registry pattern centralises engines, analyzers, insights, quality checks, and forecast methods.
dependency: pandas · rapidfuzz · openpyxl · python-calamine

Filing lifecycle

The auditable path a record takes from upload to delivered report.

Create filing ─▶ Upload file(s) ─▶ Validate bytes ─▶ Quality verdict ─▶ Status: submitted
                                    │                                    │
                              (valid / warn / invalid)                   ├─▶ under_review
                                    │                                    ├─▶ report_ready
                              invalid ─▶ rejected                        └─▶ closed
                                                                               │
                                                                   attach report ─▶ delivered

Every transition writes a StatusEvent in the same transaction as the change:
  actor · previous status · new status · note · timestamp

Filings

Each filing has a stable sequential reference (e.g. AP-2026-0001) from a database sequence, belongs to one pharmacy, carries a lifecycle status, and exposes a server-written timeline that auditors read directly.

Files

Files are staged unattached and bound to a filing only on completion, so an interrupted transfer cannot leave a half-created filing. Each is checked against its bytes, hashed (SHA-256), size/extension/path guarded, and given a validation state.

Reports

A report is attached by a super admin, records who produced it, stores structured results separately from the source document, and is immutable once delivered. Correction means reopening the filing — an audited act.

Pharmacy worker

Can: see and create filings for their own pharmacy; upload dispensing files; follow their filings' status timeline.

Cannot: see any other pharmacy's filings (including siblings); change a filing's status; invite users or read reports.

05

Feature set

The eight pillars of the product as described by the code.

File ingestion

CSV and XLSX from a pharmacy system, inspected against the stored bytes rather than the filename.

  • Real CSV parse: row/column counts and detected columns come from the actual header row (RFC-4180 splitter handles quotes/escapes).
  • Filing manifest requires NDC code and Batch number columns; a missing one is refused with the missing names.
  • Workbooks checked as ZIP containers — a fake .xlsx is rejected.
  • SHA-256 over stored bytes; size, extension, and path-traversal guards on every key.
  • Files staged unattached, bound only on completion.

Validation intake

Each file returns valid / warning / invalid, with the reason in words, derived from the bytes.

  • Three verdicts, each carrying an actionable sentence rather than a boolean.
  • Ragged rows produce a warning naming how many were padded/truncated.
  • Findings are stored against the filing, not recomputed per page load.
  • Per-cell content analysis and workbook sheet parsing at intake are not yet implemented (tracked on the compliance page).

Chain of custody

Every state change is written server-side in the same transaction as the change, and can be read back.

  • Server-written status events: actor, previous state, new state.
  • The audit event is part of the transaction — a failed transition leaves no gap.
  • Stable references (AP-2026-0001) from a database sequence, not the browser.
  • The timeline auditors see is the same history — no second display copy.

Reporting

A review ends in a report attached to the filing, immutable and exportable.

  • Reports attached by a super admin; record who produced them.
  • Structured results stored separately from the source document.
  • A delivered report is never silently replaced — reopen the filing (itself audited).
  • Raw documents served through an authorised endpoint, never a public URL.

Tenant isolation

Associations and pharmacies are separate customers in one deployment; the separation is enforced by the server.

  • Tenant scope derived from the session on every request; no route accepts scope from the client.
  • Users, filings, files, and reports filtered by caller's association/pharmacy.
  • Probing another pharmacy's filing id returns a refusal, not an empty page.
  • Permissions live in one module with a written specification.

Roles & access

Four roles, each with a documented boundary, and invite-only account creation.

  • Super admin: every association; moderator: everything read-only; association admin: their own; worker: only their pharmacy.
  • Attachments and report production are super-admin actions.
  • No self-registration — an admin issues a single-use invitation.
  • Deactivating a user ends their sessions immediately.

Notifications

The events worth an email are sent; the rest stay in the timeline.

  • Invitations, status changes, and report delivery are emailed.
  • Delivery is best-effort by design — a mail outage never fails the triggering action.
  • The timeline remains the record of truth, so a bounced email cannot lose an audit event.

Retrieval

Find a filing by reference, pharmacy, status, or date without opening every row.

  • Filter by status, pharmacy, and date range from the filing list.
  • References are unique and sequential, so a filing can be cited unambiguously.
  • Dashboard aggregates are computed from the same scoped rows the user can see.

How requests are gated — and what the gate is not

A request-time proxy keeps signed-out visitors off the workspace and the server-rendered shell. It lists 28 public paths and is deliberately implemented as a matcher with a public-path exception list, so a newly added authenticated route is protected by default rather than by remembering to add it somewhere. /dashboard is intentionally absent from the list — it renders its own signed-out state instead of bouncing, which avoids a redirect loop.

Honest limitation: the proxy is a UX shortcut, not an authorization boundary. It runs on the Edge runtime, cannot reach the database to verify a session, and cannot see a role. A cookie can be replayed, so passing the gate means nothing about identity. Real enforcement lives in lib/auth.ts and lib/permissions.ts, which every API route calls — those return 401/403 and derive tenant scope from the session. Pages under app/(app)/ are still client components and do not yet resolve the caller server-side (tracked in docs/PLAN.md, Phase 2), which is precisely why nothing sensitive may be rendered from those pages. Closing that is the honest next hardening step, not a footnote.

Analysis pipeline

Seven ordered, registry-registered stages run per file. Everything downstream of rows sees a clean transactional view.

read bytes ─▶ file_reader (csv / excel / json) ─▶ DataFrame
   │
   ├─ profile            (order 10)  column dtypes, ranges, cardinality, kind
   ├─ classification     (order 20)  header + content → canonical field map, schema category
   ├─ quality            (order 30)  6 registered checks → 0–100 score + findings
   ├─ rows               (order 35)  drop spacer/blank/repeated-header rows (profile+quality still saw them)
   ├─ domain             (order 40)  run matching domain engine(s) on the clean frame
   ├─ insights           (order 50)  13 registered rules → insight bundle
   └─ forecast           (order 60)  holdout-selected method + prediction interval
   │
   └─▶ reporting → JSON report / client report (siroq.client.v1)

File readers

csv, excel, json — each registered as a file_reader; workbooks can expose multiple selectable sheets.

Classification

Fuzzy header matching (rapidfuzz) plus value-type inference (date/number/category/text). Monetary fields only accept numeric sources; ratio/percent headers can never fill money fields; price/cost/profit/stock are header-matched only.

Schema category

Column headers are tokenised and scored against strong/weak token sets across 8 categories; this is what selects the domain engine(s) to run.

Domain analytics engines

Eight pluggable engines, one per business category; each is selected by detected schema category and contributes its own metrics.

Sales

Revenue, transactions, basket behaviour.

Inventory

Stock on hand, batches, expiry, waste/write-offs.

Purchase orders

Ordered vs. received, unit cost, supplier fills, VAT.

Prescriptions

Rx volume, days supply, prescriber behaviour, controlled drugs.

Products

SKU/NDC catalogue, generic vs. brand, strength, therapeutic class.

Patients

Cohort/adherence signals, demographics.

Payers

Claims, rejections, copay/coinsurance, reimbursement mix.

Suppliers

Vendor fill rate, lead time, contract pricing.

Engines are registered via @domain_engine("<category>") in a single module per category and dispatched through a shared registry (app/analytics_service/registry.py), so a new business domain is one file plus one decorator.

Data-quality checks

Six registered checks; each non-pass deducts a penalty from a 100-point score (an unreadable/empty frame scores 0).

CheckPenaltyPurpose
header_confidence5How confidently the columns were recognised.
empty_or_null50Blank/empty data — the heaviest signal.

Structural rows (blank spacers, repeated invoice headers) are removed before money is aggregated — but profiling and quality deliberately still see every row, because that is a fact worth scoring about the file.

16

Forecasting

Classical, reproducible, holdout-validated. No LLM — every method is deterministic.

Candidate methods (registry order)

  • naive — last value carries forward
  • mean — historical mean
  • moving_average — win = 3 and win = 7 variants
  • linear — linear trend
  • damped_trend — damped Holt (φ = 0.9)
  • seasonal — weekly seasonality (period inferred from median step)
tie-break: registration order, then order meta

How a forecast is produced

  • A daily series is built (date column auto-detected; sum|mean|count aggregation).
  • Requires ≥ 6 points; horizon 6 days; last 18 history points retained for the client chart.
  • Each candidate is scored on a holdout; the winner is refit on the full series.
  • A prediction interval is attached to every projected point (interval sparse-bounded so short series still band correctly).
  • Median step_days is inferred and used for seasonality and projected dates — sparse inputs project to correct calendar dates.

The same file always yields the same forecast. AI/RAG-based forecasting is designed (see docs/AI_FORECASTING.md) but explicitly not wired into production.

Report contract

The shared siroq.client.v1 envelope that lets the client render nested, rich results without re-parsing.

Tagged node types

  • $chart — bar series (cap 12 bars) or table, with the primary revenue/volume series.
  • $forecast — method, retained history, projected points each carrying Low/High bounds.
  • $notes — advisory caveats surfaced under "Caveats" in the panel.
  • All three are additive; untagged legacy results still render unchanged.
  • Object list-items are legal only inside tagged subtrees (enforced by a verifier).

Rendering

  • Client report-panel dispatches on node type before falling back to recursive branch rendering.
  • report-chart is hand-rolled SVG (bar, table, forecast band) — deliberately no chart dependency.
  • Forecast band aligns correctly even on sparse series (recent fix to anchor/projection spacing).

Known gaps & roadmap

An honest read: what is deliberately not shipped yet, so nothing here is overstated.

Not built absent today Planned designed, not wired Shipped live and verified

Known limitations

  • Planned Workspace pages are client-rendered. Routes under app/(app)/ do not yet resolve the caller server-side, so they must fetch data through the authorised API rather than reading the database directly. Tracked in docs/PLAN.md, Phase 2. The API layer is fully scoped and enforced; this is a rendering-path gap, not an authorization gap.
  • Planned lib/scopes.ts is fully applied for uploads; the PLAN.md note that it is "still open for application/listing routes" is stale relative to the current route code, which does derive scope per request — verified by verify:authz.
  • Not built Per-cell content analysis (date ranges, quantity types, NDC format) — tracked on the compliance page.
  • Not built Workbook sheet contents are not parsed at intake; an .xlsx is validated as a container and parsed on demand.
  • Planned Per-cell analysis is shown as a paid-tier feature on the comparison table but is not implemented — a marketing promise ahead of the code.
  • Planned Audit-trail export, data-residency options, and custom DPA/retention are Enterprise commitments not yet productised.
  • By design Dashboard aggregates are computed client-side over the already tenant-filtered row set rather than in SQL — a deliberate trade (one query, one filter, no second derivation), documented in PLAN.md 3.6.

Roadmap — the wired-up product (from docs/PLAN.md Phases 7–8)

  • Not built Phase 7 — the analytics client. lib/analysis.ts: an X-API-Key client for the service's analyse and report endpoints. This is what closes the integration gap in section 02.
  • Not built Never join by name. The service has its own applications table with a different meaning; the client must join through analysisApplicationId — a correctness trap called out explicitly in the plan.
  • Not built Persist service results to Report with resultData normalised, rawData untouched, source: "service", and engineVersion recorded.
  • Not built Log every service call in AnalysisRun (request / response / error) so failures become retryable. The model and AnalysisRunStatus enum already exist in the schema; only the write path is missing.
  • Not built Phase 8 — a real test matrix. Vitest covering 4 roles × scoping including cross-tenant attempts, which the plan itself calls "the highest-value tests in the project". Today this is enforced by executable verifier scripts instead.
  • Not built Phase 8 — rate limiting on auth and upload endpoints.
  • By design Forecast caching — /forecast recomputes deterministically per call. Acceptable while it is not called from the app; worth revisiting once it is.
  • Planned AI/RAG-assisted forecasting (docs/AI_FORECASTING.md) — architecture and non-goals documented; no provider SDK, raw files never sent externally, LLM never produces numeric forecasts.

Owner summary

SiroQ today is a working, tested, security-conscious filing platform with a real analytics backend: four enforced roles, tenant isolation proven by verifier scripts, an auditable lifecycle, and a deterministic pipeline that turns messy pharmacy files into margin, stock, expiry, and forecast insight. The deliberate boundary is trust over flash — no LLM touches customer data, and the AI capabilities on the roadmap are designed to keep it that way. The clearest near-term wins are the shipped-but-unbuilt per-cell validation, forecast caching, and closing the client↔service orchestration gap.
